# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## This is an educational project

Readability and understandability come first: someone should be able to read the source to learn how a small Lisp is built. Prefer the simple, explicit design over the clever one, name things for what they mean, keep comments for the why, keep modules small and each with one job, and delete code that does not pay for itself. There is one engine: the bytecode VM (`src/vm/`: `compiler.zig` compiles, `exec.zig` runs). A speed-up or a simplification is only kept if the tests pass and `make bench` does not get slower (see Tests).

## Commands

```bash
make                       # build ./tinylisp (Zig 0.17, ReleaseSafe: bounds/overflow checks, links libc)
make test                  # REPL and Lisp suites, collector stress, microgpt output
make lint                  # zig fmt --check, zig ast-check, spec/repo_rules.py
make check-all             # make test && make lint
make fmt                   # zig fmt src/
make bench                 # bench/run.py: 18 programs in Python and tinylisp (ARGS="-n 1 nbody")
./tinylisp [-f file.lisp] [--debug]
```

## Architecture

`src/` is one entry point and four units; each file has one job:

```
src/repl.zig              the entry point: CLI and REPL, sets up the root scope (primitives, natives, stdlib.lisp)
src/runtime/              what the compiler, the VM and the natives share
    value.zig             V (NaN-boxed), the objects it points to (Lst, Fn, Lam), constructors and tests, the printer, the error value (errv, fail)
    gc.zig                the memory manager: allocation, mark-sweep, the roots, pinned values
    scope.zig             Env, the global table, epoch, lookup and assignment, closures, scope recycling
    node.zig              the typed AST: Node, Code, Ref, Def, Proto, Guard, Sym
    machine.zig           Frame, Machine, Go, the ks/vs stacks, natives that call back into Lisp (start/step/finish/callback/tail), try/recover, the trampoline
    continuation.zig      call/cc: capture and re-enter the ks/vs snapshot of the current machine run
    primitives.zig        + - car cons ...: `prim` specialised per Op, `numeric`, and `fast`/`fast1`, the in-place forms the VM uses
src/lang/                 the language front end and the machine loop
    parser.zig            text -> AST (lists of values), iteratively
    expand.zig            macros: runs them over a whole top-level form before it is compiled or run, and carries out defmacro
    compile.zig           (expanded) AST -> typed nodes: intern, special forms, calls; refuses code nested deeper than `max_depth`
    eval.zig              the machine loop (exec/run): hands bytecode to vm/, applies lambdas and natives, returns into frames
src/vm/                   the one execution engine
    bytecode.zig          the format: Opcode (each instruction documented), Ins, Bytecode
    scan.zig              which names of a function get fixed slots: its parameters and every name defined in its body
    compiler.zig          nodes -> bytecode (gen, primitives, inlining, loops), `ready` (a function, on its first call), `top` (a top-level form)
    exec.zig              the executor
src/lib/                  the standard library
    natives.zig           map each reduce apply range zip print partial concat, the file natives read-file write-file split, load and eval
    source.zig            a file's text, and running a file form by form (for the REPL's -f and the stdlib)
    stdlib.lisp           the Lisp part, loaded at start (path relative to the repo root)
```

**Dependency direction**: `runtime/` <- `lang/parser`, `lang/compile` <- `vm/` <- `lang/eval` <- `lang/expand` <- `lib/` <- `repl.zig` (an arrow reads "is used by"); a file imports the specific module it uses, there are no forwarding files. The exceptions are few, and these are all of them:
- `runtime/` -> `vm/bytecode.zig`: `Proto`, `Frame` and `Go` point to a `Bytecode` and `scope.bind` reads the slot names from it. `bytecode.zig` is pure data (it imports `runtime/` only), so this is a cycle between two data files, not between behaviours.
- Inside `runtime/`: `gc.zig` and the object owners (`value`, `scope`, `node`, `machine`) refer to each other, because the collector allocates their objects and traces their roots; `value.zig` names the other parts' types only as pointers.
- `lang/expand` -> `lang/eval` (a macro is a Lisp function: `eval.exec` runs it on a nested machine) and `lang/expand` -> `vm/compiler` (`top` compiles the expanded form); `lang/eval` never calls the expander.
- `lang/eval` -> `vm/` (`compiler.ready`, `exec.exec`: it hands functions over) while `vm/` -> `lang/compile` (`top`: the nodes of a top-level form). `vm/` never imports `lang/eval`: the executor runs on the machine's stacks and returns to the machine loop.
- `lib/natives.zig` -> `lang/expand`, `vm/compiler`, `lang/parser` (`load` expands a form, compiles it with `compiler.top` and returns it as a `.vm` step to the machine, in the global scope (like `eval`); `eval` expands its form, sets the running machine's scope to the root and returns it the same way).

Keep names meaningful and the total source small; keep the machine's control flow visible in `eval.run` and `exec.exec` rather than hidden behind helpers. All Zig sources are `zig fmt` clean. Errors are Zig error unions (`error.Lisp`); the raised Lisp value is in `value.errv`.

**The pipeline**: text -> s-expression (`parser`) -> expanded s-expression (`expand`) -> typed AST (`compile`) -> bytecode (`vm/compiler`) -> run (`vm/exec`, on the machine of `lang/eval`). Everything runs as bytecode: a function is compiled on its first call, a top-level form when it is read.

**The expander** (`lang/expand.zig`) runs before anything is compiled. A program is processed one top-level form at a time: read (`parser.parse`/`parseNext`), `expand.form` (every macro call in the form, the bodies of its lambdas included, is replaced by what the macro returns, until the head is no macro; an iterative walk with an explicit stack, rebuilding only the lists that changed, and expanding an operator that is itself a form first, alone: if it changed, the form is dispatched again (macro call, quote, lambda, begin, defmacro) before any operand is visited, everything it holds (the lists being walked, the parts finished so far, macro results) pinned or on `vs` because macros run Lisp and the collector may run), then compiled and run. `expand.run` does the steps for the REPL, `source.runFile` for `-f` and the stdlib, and the native `load` (form by form, state in its native frame, in the global scope) does it inside the machine. The native `eval` expands its argument as a top-level form of its own and runs it in the global scope, never the caller's; the run is on the running machine (it sets the machine's scope to the root before returning the `.vm` step; its frame goes back to the caller's scope), so recursion through `eval` does not use the native stack. So a macro defined by one form is in effect for the next, a macro body may call functions defined by earlier forms, and redefining a macro does not touch code that was expanded already. `defmacro` is understood here, not in the stdlib: `(defmacro name (params) body...)` at top level (directly, or inside a top-level `begin` at any depth) expands and runs `(lambda (params) (begin body...))` at once and keeps the function in `scope.macros` (a table keyed by name, marked by the collector); the macro is called with the parts of the form. A special form name, or a defmacro anywhere but top level, is an error (raised while the enclosing top-level form is expanded, so none of it runs).

**The typed AST** (`lang/compile.zig`): the expanded AST of a top-level form becomes nodes (`node.Node`/`Code`: constant, variable, if, begin, &&/||, define/set!, lambda, call, `()`) all at once, when the form is compiled (no macro runs there); symbols are interned (`Sym`; scope keys compare by address; a name no scope has ever bound (`Sym.local`) is looked up in the global table directly, with the slot cached in the node). Building the nodes recurses, as do the scan and the bytecode compiler after it, so code may nest `compile.max_depth` (5000) levels deep and no more: deeper code raises `TinyLisp: expression is nested too deeply to compile (limit 5000)` before any of it runs. (Measured: ReleaseSafe overflows the 8 MB native stack at about 17,000 levels; the limit leaves a margin.) Data has no limit: `quote`d lists are never walked, and the parser, the expander and the printer are iterative. Nodes, their arrays and symbols are permanent (`gc.perm`); the AST they came from (and macro expansions) is pinned for good with `gc.pin`, so closures (`Lam.proto`) point at nodes freely.

**The bytecode** (`src/vm/`: `scan.zig` and `compiler.zig` compile, `exec.zig` runs): the first call of a function (a `Proto`) compiles its whole body to a stack bytecode (`bytecode.Bytecode`/`Ins`/`Opcode`, each instruction documented there), and its parameters and defines get **fixed slots** in the call's scope (`scope.bind` creates them all up front, the defines unbound). `eval.run` has a `.vm` step (`exec.exec` runs instructions until it needs the machine: a call, or a return) and a `vm` frame kind that resumes the code at the instruction after a call. Tail calls are `.apply`; a function calling itself in tail position in a scope no closure holds (`Env.captured`) reuses that scope. Locals are `local`/`setlocal` slot accesses; other names go through `outer`/`setouter`, which remember `(hops, index)` after the first lookup (the scopes passed have a fixed layout) and only check the key. Calls of a global primitive (`+ - * / mod < > <= >= eq? at` with two operands, `not abs floor sqrt exp log cos` with one) are instructions in function bodies, recognised by the compiler from the plain call node while the name is a global bound to the native, and fused with local/constant operands where possible; `vset!` is an instruction there too. In a top-level thunk, calls of those names are ordinary calls, and `(each ...)` / `(map ...)` with one list may use a bytecode loop after a run-time check that the names are still the natives (the loop body is compiled when the loop is entered). A call of a small global function without closures (`genInline`) is compiled into the caller, with slots of its own and its free names read as globals (`global`/`setglobal`); replacing such a function bumps `epoch` (`Proto.inlined`, `scope.replace`). `(each list (lambda (x) ...))` (so `for`) and `(map ...)` (so `for/list`) with one list are a **loop run by the bytecode**: a `loop` frame keeps the list position on the value stack and the last iteration's scope (`Frame.iter_env`, marked by the collector), which the next iteration reuses unless a closure captured it; the loop body is its own bytecode and returns to the loop with the instruction `ret`. Compiled code is valid for an epoch (`Bytecode.stamp`, `scope.epoch`); rebinding a primitive or `each` (any `Sym.inlined`), or binding such a name locally, bumps `epoch`, and a function is compiled again the next time it is called.
- The compiler accepts every function: any number of `&&`/`||` operands, defines anywhere (see "Function bodies"), a `define`/`set!` without a name or the form `()` (instructions that raise the error when, and only when, they run).
- **Top-level code** is a function without parameters (`compiler.top`, the `top` flag of the `Compiler`) that runs in the root scope (`Go.vm` with `m.e` = the root, never a new scope, so the lambdas it makes close over the root and can be inlined). It has no slots, nothing is hoisted: a name is a global (`outer`), a `define` is a global define (`assign`, which goes through `scope.set`), and the lambdas inside it are functions with the usual rules. Nothing is inlined into it. A `begin` of top-level forms is one thunk. The REPL, `-f` files, the stdlib, `load` and `eval` all run forms this way.
- A primitive rebound while a function that inlines it is running is seen only by calls started afterwards. A call of an undefined function pushes its arguments (evaluating them, with their side effects) and fails only at the call.
- Tests: `spec/specs.lisp` has "vm: ..." cases.

**The machine** (`lang/eval.zig`, `runtime/machine.zig`): explicit stack, no native recursion per Lisp call, per callback or per level of data, so there is no run-time recursion limit other than memory (the only native recursion is the compiler's, bounded by `compile.max_depth`). Pending work is a frame on the global `ks` stack (`vm`: bytecode resuming after a call; `loop`: a bytecode loop; `native`) and values are on the operand stack `vs`. The machine state is a `Go`: run bytecode from an instruction, hand a value to the innermost frame, or apply the function at `vs[b]` to the arguments after it. Tail calls (`tailcall`, the end of a top-level form) replace the current state instead of pushing a frame.
- **Natives that call back into Lisp** (`map`, `reduce`, `try`, `partial`, the trampoline and its thunks) are `Native.step` functions and run as `native` frames: their arguments stay on `vs` after the native (`vs[k.base]`), their state goes after them or in `k.i`. A step is invoked with `null` first, then with each callback's value, and returns the next `Go` via the helpers in `runtime/machine.zig`: `finish` (pop, hand on a value), `callback` (call a function, its value comes back to the frame) or `tail` (replace the frame by a call, e.g. `partial`). Plain natives (`Native.plain`) just compute a value.
- **Errors** (`error.Lisp`, value in `value.errv`) are caught by `exec`: `machine.recover` drops the frames above the innermost `try` frame of this run and resumes it with the error value, which tail-calls the handler. Without one, the run truncates `ks`/`vs` to its base (`errdefer`) and the error propagates. The trampoline's "active" flag (`s.i` = index + 1 of its run frame) is validated against `ks`, so a run frame dropped by an error doesn't leave it stuck.
- **Macro expansion** (`expand.zig`) is the only nested machine (`call` → `exec`): macro bodies run on it while a form is expanded, and running a form never nests a machine. Macro bodies are expanded too, so macros may call macros, nested to any depth, one nested machine per macro call being run.
- Parser, printer and freeing are iterative too.

**Continuations** (`runtime/continuation.zig`): `call/cc` and `call-with-current-continuation` capture the current `eval.exec` run — frames on `ks` from `Machine.base` up to (but not including) the `call/cc` frame, and values on `vs` from `Machine.vbase` up to the `call/cc` frame's `base` (as if `call/cc` had returned). A continuation is a native function whose `Fn` object has extra bytes after it: `kbase`, `vbase`, `nframes`, `nvalues`, then a `Frame` array and a `V` array; the collector traces them via `continuation.markCont` and sizes them with `contExtraBytes` (must match `gc.new(Fn, extra, ...)`). Invoking a continuation truncates the active run to that snapshot's `kbase`/`vbase`, copies the saved suffix back, and returns `.ret` with one value (zero arguments to `k` pass `nil`; more than one is an error). At capture, every `Env` and `iter_env` in the snapshot is marked `captured` through `scope.hold` (like a closure, so loop and self tail-call recycling does not reuse those scopes). Capture or invoke while `machine.macro_depth > 0` or `machine.machines.len > 1` (a macro body runs under `macro_depth`; a nested `eval.exec` can push another `Machine`) errors. A continuation captured in one top-level form and invoked from a later form resumes the rest of the captured form and its value becomes the value of the current top-level form (see `examples/continuations.lisp`). Replacing `try` or the trampoline with `call/cc` in the implementation would not simplify the machine: errors and `defrec` still need explicit frame truncation or thunks, and benchmarks should not pay for continuation machinery on code that never uses it.

**Values**: `V` is an 8-byte NaN-boxed `enum(u64)` (`V` in `runtime/value.zig`): a number is its own double (NaN is canonicalised by `V.num`), everything else is a tagged payload in the quiet-NaN space (`nil`, bool, symbol/string, string literal, list, native function, closure). Build with `V.num/boolean/string/literal/listOf/fnOf/lamOf`, read with `tag()`/`is(tag)`/`asNum/asBool/asStr/asList/asFn/asLam`; compare with `==` only for identity or `V.nil` (use `.is(.n)` and `asNum` for numbers). A list is a length followed by its items (`Lst.items()`).

**Memory (`src/runtime/gc.zig`)**: stop-the-world mark-sweep on libc malloc. Every managed object (`alloc`/`new(T, extra, kind, init)`, not zeroed: constructors set every byte they use) has a one-word header (next object | kind | mark) and sits on one list; `perm` objects (parser symbols/literals, compiled nodes, root keys, root scope) are never collected. Nothing is counted: the machine loop calls `gc.collect()` at `.vm`, and the VM at self-tail-call backedges and loop iterations once `gc.due()` says about half as much as is live has been allocated (at least 2 MB), with every live managed value reachable from a root; natives may allocate freely. Roots (`gc.markRoots`): the `ks`/`vs` stacks (frames' scopes), every running machine's scope (`machine.machines`), the global table, `gc.pin`ned values (the AST that compiled nodes refer to) and `errv`. Marking and sweeping use worklists, never recursion; cycles are collected; allocation failure exits with `TinyLisp: out of memory`.
- Anything new that holds a value outside those roots (a Zig-side global, a cache) must be marked in `gc.markRoots`.
- At collection, publish the VM stack pointer in `vs.items.len` and keep the active scope in the registered machine. A Zig local may survive collection only if its managed object is also reachable from a root; never rely on a local alone across a `.vm` step.
- **Scope recycling**: the scope of a call (`Env`, `scope.bind`) is handed back to a free list (`scope.release`) when the call ends (a tail call, or a return into a frame of another scope) if it is still `Env.recyclable` (`scope.lambda` clears that when a closure captures it). Recycling assumes only frames, `m.e` and closures hold a scope; the collector forgets the free list. A closure (`scope.lambda`) marks its scope and every enclosing one as `captured` and no longer recyclable. The exception is the lambda that is the last operand of a call of the native `each`/`map` (`Proto.guard`, set by the bytecode compiler, `guardLoopBody`, checked again when the lambda is created: the name must still be global and the same native): it only lives while the loop runs, so it captures nothing, and a `for` inside a loop body no longer costs its enclosing scope its recycling (this works only because a real closure marks the whole chain). This removes most allocation (about two thirds of all objects in microgpt).
- To stress the collector, `make test` also runs both suites on a build with the initial `limit` and the floor assigned by `collect` in gc.zig at 2048 bytes (a minimum threshold of 2 KB allocated between collections; afterwards the limit follows half the live size as usual).

## Language semantics

- **Function bodies**: the local names of a function (lambda, `defn`, `fn`, a `for` body) are its parameters and every name `define`d anywhere in its body (in a branch, an `&&`/`||` operand, a call argument, a nested `begin`...) but not inside a nested lambda, which is a function of its own. A defined name is local to the whole body (like an assigned name in a Python function) and its slot is **unbound** until the define runs; reading it while unbound raises `TinyLisp: x is used before it is defined` (never nil, never a global or outer variable of the same name; also for the branch that did not run, for a closure that reads a captured name before the define ran, and for a loop body or self tail call that starts a new iteration: each starts with its defines unbound). Parameters are never unbound. Local helpers defined in one body may call each other (letrec*-like). `define` outside any function (top-level code, also inside a top-level `begin`/`if`/macro expansion) creates or updates a global; nothing in top-level code is hoisted. `set!` of a name that no function scope and no global binds raises `TinyLisp: set!: x is not defined`; `set!` of a local whose slot is unbound assigns it. `load` and `eval` run at top level, in the global scope, never in the caller's (a loaded file defines globals; the caller's locals are untouched).
  Implementation: `V.unbound` (tag 0 of the box, never a program value; the printer panics on it) fills the defined slots (`scope.bindWith`, the self tail call, the loop's iteration scope reuse). `vm/compiler.zig` tracks which slots have certainly been defined at the code being generated (`Compiler.defined`: a define marks its slot after its value; an `if` keeps what both branches defined, the later operands of `&&`/`||` keep nothing) and reads a defined name as `local` there, as `local_checked` elsewhere. `outer` (a name of an enclosing scope) compares every value it reads with `V.unbound`; Inlined functions get slots of their own, unbound from the start of the call.
- **Macros**: `(defmacro name (a & rest) body...)` (see the expander above) makes a function of the form's parts, `(name x y ...)` is replaced by its value, again and again until the head is no macro. Top-level only (a defmacro anywhere else, or named like a special form, is an error). Each top-level form is expanded whole before it runs (REPL line; file form by form; `eval`'s argument, which runs in the global scope); macros defined by earlier forms are in effect, a macro's body and the functions it calls may use macros defined before it, and redefining a macro changes only the forms expanded afterwards. `quote`d data and a lambda's parameter list are not expanded. Numbers, booleans and nil are never macro calls. Known limitation: a macro that expands to a call of itself loops forever.
- Symbols and strings are the same type; string literals stay distinct in the AST (`.lit`) and evaluate to strings.
- `&&`/`||` are short-circuit special forms in head position (`Code` `&&`/`||`); passed as values they are the plain primitives.
- `0` and `""` are falsy, `'()` is truthy; `eq?` treats an empty list as `nil`.
- `(lambda (a & rest) ...)`: the compiler drops `&` and sets `Proto.rest`; `scope.bind` gives the last parameter the extra arguments as a list. The parser reads `'` `` ` `` `~` `~@` as `quote`, `quasiquote`, `unquote`, `unquote-splicing` forms (prefix markers on the `open` stack, negative entries); `quasiquote` itself is a Lisp macro in the stdlib (`quasi`).
- **Bootstrapping** (top of `stdlib.lisp`): `quasiquote` is a macro (`quasi`, plain functions written with `define`/`lambda`, defined first); every macro after it may use backquote. A template inside a template raises `TinyLisp: nested quasiquote is not supported` (a template inside a `~` is fine).
- Stdlib macros: `defn` (several body expressions become a `begin`), `fn` (a lambda with several body expressions), `->` (thread-first), `chain` (composes blocks; each block expression is evaluated once, as an argument of a wrapper lambda), `for` (expands to `each`, a `map` that keeps no result list) and `for/list` (expands to `map`; a pattern variable over `(zip xs ys)` becomes a multi-list `map`), `defrec`, `deftest`. `examples/autograd.lisp` adds `val` (infix arithmetic on values, Python's precedence) and `slots` (`(data v)` is `(at v 0)`).
- `map` takes several lists, `(map l1 ... ln f)`, and stops at the shortest; `range`, `zip` and `apply` are natives (a Lisp `zip`/`range` built with `cons`/`rest` is quadratic, since both copy); `flatten` is `(apply concat lst)` and `filter` builds on it.
- `defrec` rewrites self-calls into thunks and wraps the function with the native `trampoline`.

## Tests

Add a case whenever behaviour changes.
- `spec/body-scope.lisp`: the function-body rules above (early reads, branches, loops, closures, `set!`, `load`/`eval`). `spec/repl.py` has the REPL-visible ones and the compile depth limit.
- `spec/specs.lisp`: `deftest` + `assert` (the test name is a string, so it can have spaces, and by convention reads `area: what it checks`; a symbol works too; `deftest` rewrites each `(assert expr)` to carry the test name and the quoted expression, so a failure prints both; `equal?` is a deep comparison), ends with `(run-tests)`; a failing assert exits non-zero. Includes the compiler's totality (200 operands of `&&`/`||`, forms without a name, `()`), top-level code, the depth limit, and stack-safety tests (100k-deep recursion, deep data, 100k+ deep recursion through `map`/`reduce`/`partial`/`try` callbacks, errors unwinding them).
- `spec/repl.py <binary>`: drives the REPL and checks printed results (parsing, printing, errors, 100k-deep nested data, the limit on nested code).
